# Review notes

- `Model/Adapter/OptionalServiceFactory`: object manager by class name, called after the feature check, so `di:compile` passes without optional Hyvä packages.
- Constructors name only hard requirements (Hyvä CMS 1.3 incl. Media Gallery, Admin Dashboard); optional Hyvä services come from that factory.
- `Model/Auth/CallerContext` is the one adapter over the core's non-API caller classes; a public core API is proposed upstream.
- `hyva_ai.*` is monitoring only and `hyva_admin_perm.*` read only, by design; no generation or permission writes through MCP.
- Not covered on purpose (README "Not covered"): Image Editor, Admin Theme, Commerce Module, CMS Google Maps.
- Tools with `entity_type` are listed for a role holding their verbs on at least one content type (`ContentAcl::listingResource()`, the core takes one resource and no arguments) and refused per call (`-32004`) on a type the role lacks. The core sets its caller only when it dispatches a tool, so `Plugin/JsonRpc/BindCallerContextPlugin` binds it before `tools/list` and the `tools/call` ACL gate (frontend area, where `/mcp` runs).
- Store scope: menus and forms are scoped by their store views although the Hyvä admin does not scope them; stricter on purpose.
- Store scope: email/newsletter templates, linked groups and category positions have no store view; restricted roles read them, never write.
- `hyva_media.trash.restore` has no confirm: it never overwrites (skips taken paths, as Hyvä's `TrashRepository` does).
- CI runs Magento 2.4.7-p3, PHP 8.3, PHPUnit 9.5 like the sibling Magebit MCP modules; local runs use 2.4.8 / PHPUnit 10.
- Dev helpers (smoke script, test roles, absent-package env) live outside the repo on purpose; the module ships no test fixtures.
- Store scope: a product in no website stays visible to restricted roles; mirrors Hyvä CatalogProductEntityGuard.
- Store scope: catalog usages are judged by product website / category tree, not the description's store view (the usage index has no store_id).
- Media files, folders, trash and sync status are not store-scoped; the Hyvä Media Gallery has no website or store view scope (T-36: matches the core v1.3.4, which scopes nothing without a store assignment, e.g. `Tool/System/StoreList.php`, `Tool/System/Log/*`); `Model/Media/SharedMedia::DESCRIPTION_NOTE` and the Media Health notice say so.
- Store scope: the MCP Activity widget shows a website-restricted admin only their own calls (the audit log has no store view); unrestricted admins keep the global view.
- Menu Builder, Media Optimization, Media Gallery, Form Builder, Email Templates, Store Credit, Linked Products, AI Worker off: their tools return the undeclared `ContentAcl::UNAVAILABLE_RESOURCE` as listing resource, so `tools/list` hides them (`bin/magento magebit:mcp:tools:validate-acl` lists them as not resolving, by design); status tools stay (`FEATURE_MISSING_ACL_RESOURCE` override in the store credit, AI Worker and `hyva_media.status` status tools; the image and media audit tools are hidden without Media Gallery).
- Store scope, store view 0 (T-32): rules taken from Hyvä Advanced Admin Permissions — read `AllowedScopes::allowsStore()`, write/create `DataFieldWriteRule::isStoreWriteDenied()` + `GlobalWritePolicy` (every store view), re-assign judged by the new assignment with store view 0 not counted as dropped (`EntityScopeWriteGuard::unassignsForeignScope()`); `StoreScopeGuard::assertChangeable()`.
- Delete tools (T-22): `hyva_cms.page.delete` / `hyva_cms.block.delete` / `hyva_menu.delete`, confirm-gated (an entity in use also needs `force: true`, T-73); own tool resource granted to no role plus the admin delete permission (`Magento_Cms::page_delete` + `Hyva_Cms::page_delete`, `Magento_Cms::block` + `Hyva_Cms::block_delete`, `Hyva_MenuBuilder::menu_delete`) via `ContentAcl::listingResource()` as the underlying resource, re-checked in `AbstractEntityDelete::run()`. Delete goes through the repositories (`EntityWriter::delete()` in the admin area, `MenuGatewayInterface::delete()`); Hyvä rows go by FK cascade, scheduled items of pages and blocks stay as in the admin; `hyva_menu.delete` cancels the menu's pending scheduled items after the delete (T-68, no schedule-cancel permission needed: the delete permission covers its own cleanup). Replaces the round-1 "deletion is admin-only" note. T-107 adds `hyva_email.template.delete` (`Magento_Email::template` + `Hyva_EmailTemplates::email_template_delete`) and `hyva_email.newsletter.delete` (`Magento_Newsletter::template`; Hyvä has no newsletter delete verb) on `AbstractTemplateDelete`: the core model's `delete()` (Hyvä plugins prune version history, rows cascade); in use = a `core_config_data` value at any scope whose path ends in `/template` or `_template` (Magento's `BackendTemplate::getSystemConfigPathsWhereCurrentlyUsed()` reads system.xml, empty in the frontend area MCP runs in) / a `newsletter_queue` row not sent, sending or paused (sent and cancelled = history, counted as `queue_history`, cascade-deleted by Magento).
